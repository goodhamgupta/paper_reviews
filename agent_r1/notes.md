# Agent R1

- Training RL models has 3 distinct content in the ctx window:
  - User messages
  - Model messages
  - Tool outputs
- We only want to update the model based on what it has generated. For eg: We don't want to compute gradients on the model for deterministic tool calls, since these were not generated by the model(rather they were only used to inform it's next step).
- two different ways of masking:
    - Loss masks: Calculate loss on the tokens the model generated
    - Advantage Masks: Ensures that  "credit" for a good outcome is properly attributed to the specific actions the model took, skipping over determinsitic tool outputs.

## Challenge

3 different phases:
- Rollout(Inference): generate agent trajectories with tool calls
    - requies high throughput and low latency
    - benefits from tp for large batch inference
    - memory-bound (KV cache dominates)
- Training (backward): update model params via PPO/GRPO
    - requies gradient computation across long sequences
    - benefits from data parallelism (DP) and FSDP
    - compute bound(grad accumulation, optimizer updates)
- Reference policy: compute reference log probabilities
    - Similar to rollout but read-only
    - can be offloaded to cpu or share GPUs strategically.

### Hybrid engine

- Most tricky part
- switches between trianing and inference mode
- Training (FSDP)
    - MOdel sharded across GPUs using Pytorch FSDP
    - Ech gpu holds a fraction of params
    - support gradient checkpointing to reduce memory
- inference:
    - model loaded with TP for fast generation
    - kv cache managed by vLLM for batched inference

**Sync**:

Managed by FSDPVLLMShardingManager
- Before roolout: FSDP state_dict -> vLLM weights
- after actor update: vLLM stays dormant. FSDP handles all gradient update
- repeat for next iteration

### Training loop workflow

Single training step:

1. Rollout vLLM: generate trajectories with tool calls
    - Actor in inference mode(TP=2, for eg)
    - tool environment executes actions
    - create action_mask(1=model_tokens, 0=tool_outputs)
2. Compute rewards: evaluate trajectory quality
    - Reward functions runs on driver process
3. reference policy: compute KL penalty
    -  RefPolicy worker(vLLM mode)
4. Critic (PPO only): estimate values
    - critic worker(FSDP mode)
5. Advantage estimation: Compute GAE or GRPO advantages
    - User action_mask to only credit model actions
    - Driver process(lightweight computation)
6. Actor update: train policy via PPO
    - switch to fsdp training mode
    - mini-batch iteration with grad accumuulation
    - clip gradients and update params
    - sync weights back to vLLM for next rollout

### Parallelism strategy

- DP -> Each GPU processes different micro batches. Same model available on all GPUs.
- TP -> Used in vLLM rollout. Model layers split across GPUs
    - TP=2, each attention head subset runs on different GPUs
- FSDP: Pytorch native sharding for training
    - params sharded across GPUs
    - gradients computed lcoally, then all-gathered

### Memory optimisation techniques

- Gradient checkpointing: Recompute activations during backward pass
- CPU offloading: Move params/optimzer states to CPU when not needed
- Dynamic batch sizing: auto adjust batch size based on seqlen
